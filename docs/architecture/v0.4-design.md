# Space Sheriff v0.4 可靠性设计

状态：Accepted  
目标版本：v0.4.0  
基线版本：v0.3.0

## 1. 背景

v0.3 已具备大文件扫描、重复文件检测、排除规则、清理计划和结果导出，但扫描结果与清理过程仍主要存在内存中。应用重启后计划会丢失，重复扫描会重复计算文件哈希，清理中断也缺少可审计记录。

v0.4 不扩展新的清理类别，重点把现有能力变成可恢复、可审计、可验证的本地数据流程。

## 2. 目标与非目标

### 目标

- 使用本地 SQLite 保存扫描会话、文件索引、哈希缓存、清理计划和清理事务。
- 通过稳定文件身份识别硬链接，避免把同一物理文件误判为重复文件。
- 文件身份、大小和修改时间未变化时复用 SHA-256，减少重复扫描成本。
- 清理前持久化事务和项目快照；每个文件移动到回收站后立即记录结果。
- 应用异常退出后，将未完成事务标记为中断并保留审计信息。
- 保持单文件应用、离线运行和 Windows/macOS 四个现有构建目标。

### 非目标

- 不自动删除文件，不绕过系统回收站。
- 不实现云同步、账户、多用户共享或远程控制。
- 不承诺跨卷、跨重启永远不变的文件身份；缓存命中仍必须校验大小和修改时间。
- 不在 v0.4 实现系统级后台服务、定时扫描或自动清理策略。

## 3. 架构

```text
Web UI
  │ HTTP + session token
  ▼
Local Go server
  ├── Scanner ── file identity ── hash cache
  ├── Cleanup planner ─────────── persisted plan
  ├── Trash adapter ───────────── cleanup journal
  └── Store ───────────────────── SQLite database
```

数据库位于用户配置目录的 `SpaceSheriff/index.db`。可用
`SPACE_SHERIFF_DATA_DIR` 覆盖目录，便于测试和便携部署。目录权限在支持的平台上设为
`0700`，数据库文件不存储文件内容，只存储路径、元数据、摘要和操作结果。

SQLite 使用纯 Go `database/sql` 驱动，确保 `CGO_ENABLED=0` 的交叉编译不变。
连接启用外键、忙等待和 WAL；迁移与关键状态变更均使用事务。

## 4. 数据模型

初始 schema 版本为 1。

### `scan_sessions`

| 字段 | 含义 |
| --- | --- |
| `id` | 随机会话 ID |
| `root` | 扫描根目录 |
| `state` | `walking`、`hashing`、`completed`、`cancelled`、`failed` |
| `started_at` / `completed_at` | Unix 纳秒时间 |
| `files_seen` / `bytes_seen` | 扫描统计 |
| `errors` / `excluded` | 错误和排除数量 |
| `hashes_reused` | 复用哈希数量 |

### `files`

| 字段 | 含义 |
| --- | --- |
| `identity` | 平台文件身份，主键 |
| `path` | 最近一次看到的绝对路径 |
| `size` / `modified_at` | 缓存校验条件 |
| `physical_size` / `link_count` | 物理占用与硬链接信息 |
| `sha256` / `hash_updated_at` | 内容摘要及更新时间 |
| `last_seen_session` | 最近扫描会话 |

同一身份出现多个路径时，扫描结果可以展示路径，但重复文件候选只保留一份物理文件。
路径变化不使哈希缓存失效；身份、大小或修改时间变化会使缓存失效。

### `cleanup_plan`

保存路径、大小、修改时间、文件身份、显示所需记录快照和加入时间。写入采用“整份替换”
事务，使 UI 中的计划与数据库保持一致。应用重启后可恢复计划。

### `cleanup_transactions` 与 `cleanup_items`

事务记录总计划字节、实际释放字节和整体状态；项目记录执行前快照、逐项状态与错误。
路径只作为用户可读定位信息，执行前还会检查大小和修改时间，防止文件被替换后误清理。

## 5. 状态机

### 扫描

```text
walking ──► hashing ──► completed
   │           │
   ├───────────┴──────► cancelled
   └──────────────────► failed
```

每次扫描先创建会话。状态和最终计数在单次数据库事务中更新。启动时遗留的
`walking` 或 `hashing` 会话标记为 `failed`，原因记为上次进程中断。

### 清理

```text
prepared ──► executing ──► completed
                 ├───────► partial
                 └───────► failed
```

项目状态为 `pending`、`trashed`、`failed` 或 `skipped_changed`。执行顺序：

1. 校验请求、会话令牌和计划快照。
2. 在事务中创建 `prepared` 记录和全部 `pending` 项目。
3. 将事务改为 `executing` 并提交，之后才允许移动文件。
4. 每移动一个文件，单独提交该项目结果。
5. 汇总为 `completed`、`partial` 或 `failed`。

应用启动时，遗留的 `executing` 事务改为 `interrupted`。系统回收站操作无法和 SQLite
组成原子事务，因此数据库是意图和结果日志，不声称能够自动回滚文件移动。

## 6. 文件身份和硬链接

- macOS：设备号与 inode 组成身份。
- Windows：卷序列号与文件索引组成身份。
- 无法取得平台身份时：使用规范化绝对路径作为保守降级身份，并禁用跨路径硬链接合并。

身份只用于本地优化和去重。删除前始终重新读取文件信息，并至少比较路径、大小和修改时间。
硬链接的多个目录项共享内容；重复检测只计算一次哈希，也不把这些目录项互相报告为可释放空间。
macOS 的物理占用来自文件系统块数；Windows v0.4 在无法取得分配大小时保守回退为逻辑大小。

## 7. 一致性与故障恢复

- schema 迁移在独占事务内完成，失败时应用拒绝继续写入并显示明确错误。
- 不支持数据库降级迁移；旧版本应用遇到更高 schema 版本时拒绝打开。
- 扫描索引按小批次写入，避免长事务阻塞计划和清理日志。
- 清理日志优先于吞吐量；每项结果立即落库。
- 数据库损坏时不尝试静默重建。用户可以备份后移走数据库，应用再创建空库。
- 仅定期删除已完成的旧扫描会话；清理事务默认保留，v0.4 不自动删除审计记录。

## 8. 威胁模型

| 风险 | v0.4 控制 |
| --- | --- |
| 网页诱导本地接口执行清理 | 仅监听回环地址、要求进程内随机会话令牌 |
| 扫描后文件被替换 | 清理前重新校验大小和修改时间，不一致则 `skipped_changed` |
| 符号链接逃逸 | 扫描不跟随符号链接；只处理扫描得到的普通文件 |
| 硬链接虚增可释放空间 | 稳定身份合并同一物理文件 |
| 应用在清理中崩溃 | 预写事务、逐项结果、启动恢复为 `interrupted` |
| 路径和摘要隐私泄露 | 数据仅存本机用户配置目录，不上传、不写遥测 |
| 数据库被其他本地进程修改 | 文件权限、schema 校验、执行时再次检查文件元数据 |

具有当前用户权限的恶意本地进程仍可修改应用数据库或文件；v0.4 不试图建立高于操作系统账户
权限边界的信任模型。

## 9. 性能目标

以下是开发验收目标，不是所有硬件上的服务等级承诺：

- 10 万文件扫描时，索引写入不为每个文件新建数据库连接。
- 未变化文件的第二次重复检测应复用哈希，复用数量可在状态/API 中观察。
- UI 状态轮询期间，SQLite 写入不应让本地接口出现持续性阻塞。
- 数据库增长与扫描文件数线性相关，不保存文件内容。

## 10. API 与界面变化

- `GET /api/plan`：读取持久化清理计划。
- `POST /api/plan`：用路径列表原子替换计划。
- 批量清理响应增加 `transactionId` 和逐项最终状态。
- 扫描状态增加 `hashesReused`。
- UI 启动时恢复计划；扫描完成后仍保留未再次出现的计划快照并明确显示。

现有导出格式保持兼容；新增字段只做向后兼容扩展。

## 11. 验收标准

1. 新库、已迁移库和高版本库均有自动化测试；高版本库必须安全拒绝打开。
2. 相同文件第二次扫描可复用哈希；大小或修改时间改变后不得复用。
3. 硬链接不会形成重复文件组，也不会重复计算可释放空间。
4. 清理计划在关闭并重新打开 Store 后保持一致。
5. 清理事务在移动前存在；逐项成功、失败、文件变化和进程中断均可查询。
6. 所有删除仍进入系统回收站，且文件变化时默认跳过。
7. `go test -race ./...`、覆盖率检查和四个目标构建全部通过：
   `darwin/amd64`、`darwin/arm64`、`windows/amd64`、`windows/arm64`。
8. README、发布说明和界面准确描述 v0.4 行为，不宣称无法保证的自动回滚能力。

## 12. 后续边界

v0.5 才考虑定时扫描、规则引擎、数据库维护 UI、签名更新、企业策略和集中审计。它们不得反向扩大
v0.4 的实现范围。
