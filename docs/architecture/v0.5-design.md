# Space Sheriff v0.5 可治理性设计

状态：Accepted  
目标版本：v0.5.0  
基线版本：v0.4.0

## 1. 背景

v0.4 已经建立本地索引、增量哈希、持久化清理计划和清理事务日志。下一步不是继续增加更多
“可删除文件类型”，而是让规则来源、操作记录和数据库状态对用户可见、可配置、可审计。

v0.5 的主题是本地可治理性：版本化策略、审计中心和数据库健康维护。

## 2. 目标与非目标

### 目标

- 将现有清理判断参数化为版本化策略包，并内置稳健、均衡、空间优先三种策略。
- 允许导入经过严格校验的本地 JSON 策略，记录导入与启用事件。
- 核心系统目录保护、个人文件复核和未知文件复核不允许被策略关闭。
- 清理事务记录执行时使用的策略 ID 和版本。
- 提供只读审计中心，查看事务状态、计划与实际释放空间及逐项结果。
- 提供数据库健康信息、快速完整性检查、WAL checkpoint 和 SQLite optimize。
- 从 SQLite schema v1 安全迁移到 v2，同时支持全新安装。

### 非目标

- 不执行策略中的脚本、表达式、正则表达式或外部程序。
- 不提供永久删除、清空审计记录或自动批准清理。
- 不实现系统级后台服务。应用退出后不会定时扫描。
- 不实现云端策略分发、集中审计或遥测。
- 不实现自动更新与代码签名。它们需要发布基础设施、证书和独立威胁模型。

## 3. 策略模型

策略包是有固定 schema 的 JSON 文档：

```json
{
  "id": "balanced",
  "name": "均衡",
  "version": 1,
  "description": "兼顾安全与空间回收",
  "installerMinAgeDays": 30,
  "cacheMinAgeDays": 7,
  "cacheHighConfidenceDays": 30,
  "archiveMinAgeDays": 90,
  "largeStaleMinAgeDays": 180,
  "largeStaleMinBytes": 10737418240
}
```

固定决策顺序保持不变：

1. 核心系统路径 → `danger`
2. 达到策略阈值的旧安装包 → `safe`
3. 个人目录或个人文件类型 → `review`
4. 缓存、临时文件和日志 → 根据策略年龄阈值判断
5. 受保护系统或应用目录 → `danger`
6. 达到策略阈值的压缩包或超大陈旧文件 → `review`
7. 其他未知文件 → `review`

策略只能调整天数与字节阈值，不能改变上述顺序、风险级别或保护集合。

### 内置策略

| 策略 | 适用场景 | 缓存最低年龄 | 安装包最低年龄 | 陈旧大文件 |
| --- | --- | ---: | ---: | --- |
| `conservative` | 生产机、重要工作站 | 30 天 | 60 天 | 20 GB / 365 天 |
| `balanced` | 默认个人电脑 | 7 天 | 30 天 | 10 GB / 180 天 |
| `reclaim-focused` | 空间紧张、仍由用户复核 | 3 天 | 14 天 | 5 GB / 90 天 |

“空间优先”仍不自动删除，也不能降低系统和个人文件保护。

### 校验边界

- ID：1–64 个 ASCII 小写字母、数字、连字符；自定义 ID 不能覆盖内置 ID。
- 名称与描述分别不超过 80 和 300 个 Unicode 字符。
- 版本：1–1,000,000。
- 天数：1–3,650，且高置信缓存天数不得小于缓存最低年龄。
- 大文件阈值：1 GiB–100 TiB。
- JSON 请求最大 512 KiB；拒绝未知字段，避免拼写错误被静默忽略。

策略切换只影响后续扫描。已有扫描结果和清理计划保留当时的建议快照，直到重新扫描。

## 4. SQLite schema v2

### `policy_profiles`

| 字段 | 含义 |
| --- | --- |
| `id` | 策略 ID，主键 |
| `name` / `description` | 用户可读信息 |
| `version` | 策略文档版本 |
| `built_in` | 是否内置；内置策略不可被导入覆盖 |
| `document` | 经过校验的规范 JSON |
| `created_at` / `updated_at` | Unix 纳秒时间 |

### `settings`

键值配置。v2 仅使用 `active_policy_id`，默认 `balanced`。

### `governance_events`

保存策略导入、策略启用和数据库维护事件。字段为事件 ID、类型、发生时间和有限长度的 JSON
详情。事件不包含文件内容。

### `cleanup_transactions` 扩展

增加 `policy_id` 与 `policy_version`，记录清理执行时的活动策略。v1 事务迁移后标记为
`balanced@1`，表示历史兼容默认值，不反推当时真实配置。

## 5. 迁移与兼容

```text
新库 ──► schema v1 ──► schema v2
旧 v1 库 ───────────► schema v2
高于 v2 的库 ───────► 安全拒绝打开
```

- 每个版本迁移使用独立事务。
- v2 迁移失败时 v1 数据保持可读，不部分启用 v2。
- 启动后幂等写入内置策略，并确保活动策略存在。
- 旧版 v0.4 无法打开 v2 数据库；这是有意的单向 schema 升级，发布说明必须明确。

## 6. API

### 策略

- `GET /api/policies`：活动策略和全部策略摘要/文档。
- `POST /api/policies/activate`：`{"id":"balanced"}`。
- `POST /api/policies/import`：提交完整策略 JSON；成功后保存但不自动启用。

### 审计

- `GET /api/audit?limit=50`：最近清理事务，limit 范围 1–100。
- `GET /api/audit?id=<transaction-id>`：事务及逐项结果。

### 数据库健康

- `GET /api/maintenance`：schema 版本、数据库/WAL 大小、索引文件数、扫描会话数、
  清理事务数、计划项目数和 `PRAGMA quick_check` 结果。
- `POST /api/maintenance`：仅接受 `checkpoint` 或 `optimize`。

所有 API 继续受回环监听、Host 校验和会话令牌保护。

## 7. 审计与维护状态

审计中心默认显示最近 20 条清理事务：

- 时间、状态、策略版本
- 计划文件数与计划字节
- 成功、失败、变化跳过数量
- 实际释放空间

展开事务时读取逐项路径、状态和错误，不一次返回整个历史。

维护动作：

- `checkpoint`：执行 `PRAGMA wal_checkpoint(TRUNCATE)`，回收已合并的 WAL 空间。
- `optimize`：执行 `PRAGMA optimize` 后再 checkpoint。

维护期间 Store 只有一个数据库连接，因而与扫描索引写入串行，不产生并发写冲突。UI 在扫描运行时
禁用维护按钮，避免造成可感知的扫描停顿。

## 8. 威胁模型

| 风险 | v0.5 控制 |
| --- | --- |
| 恶意策略放宽系统保护 | 保护顺序和风险级别编译在应用中，策略只能调整阈值 |
| 策略 JSON 注入或资源消耗 | 固定结构、拒绝未知字段、字段范围与请求大小限制 |
| 内置策略被覆盖 | `built_in` 记录与导入 ID 冲突检查 |
| 审计接口泄露路径 | 仅回环服务、随机令牌、无跨域开放、无上传 |
| 维护操作破坏数据 | 不暴露 SQL、VACUUM、删除或重建；仅固定白名单动作 |
| 数据库损坏被静默忽略 | 展示 quick-check 结果；损坏时不自动抹除数据库 |
| 历史记录伪装策略来源 | 事务固化策略 ID/版本，治理事件记录切换时间 |

拥有当前操作系统账户权限的恶意本地进程仍可修改数据库；v0.5 不提供高于账户权限的防篡改保证。

## 9. 界面

新增“治理中心”卡片：

- 活动策略选择器、策略说明、启用按钮
- 自定义策略 JSON 导入区域
- 数据库健康摘要与维护按钮
- 最近清理事务表和逐项详情

治理中心默认折叠，避免干扰扫描主流程。危险能力不会因为选择“空间优先”而自动执行。

## 10. 验收标准

1. 新库和真实 v1 fixture 均迁移到 v2；数据保留，高版本库仍被拒绝。
2. 三个内置策略不可覆盖，活动策略在重启后保持。
3. 非法 ID、未知字段、越界阈值和保护冲突均被拒绝。
4. 同一测试文件在三种策略下产生预期且可解释的不同建议。
5. 新扫描使用活动策略；旧结果不在策略切换时静默变化。
6. 清理事务保存策略 ID/版本，审计列表和详情统计正确。
7. quick-check、checkpoint 和 optimize API 有测试，未知维护动作被拒绝。
8. UI 可以切换策略、导入策略、查看数据库健康和最近审计，首次启动无控制台错误。
9. `go test -race ./...`、覆盖率门槛、`go vet`、前端语法检查和四平台无 CGO 构建通过。

## 11. 后续边界

v0.6 可设计真正的后台扫描代理和 OS 任务注册；v0.7 再考虑签名更新、企业策略签名和集中审计。
这些能力需要独立进程生命周期、密钥管理、服务端协议和运维模型，不在 v0.5 中模拟实现。
