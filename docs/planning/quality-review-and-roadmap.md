# Space Sheriff 质量审查与未来路线图

审查日期：2026-08-02
审查分支：`agent/v0.6`
审查基线：`0322458`（`fix: harden scheduled scan workflows`）

## 1. 结论

v0.6 的 Go 便携版已经满足“可构建、可运行、后台只读、主要安全边界有自动化回归”的发布候选基础。
本轮没有发现后台自动清理或绕过当前扫描结果直接删除文件的路径。

v0.7 已在隔离副本中实现并通过自动化回归，v0.8 开发版已在其上加入大规模扫描和资源预算基础能力。以下 v0.6 审查项已在本轮处理；真实双平台任务和签名应用仍需实机验收。

本轮处理包括：

1. 清理 API 增加 `movedBytes`，界面改为“已移入回收站逻辑大小”，旧 `released` 字段保留为兼容别名；
2. 恢复逻辑识别新鲜的计划租约，不再误判长时间有效扫描；
3. 退出程序会取消并等待活动扫描，再优雅关闭 HTTP/SQLite；
4. 前台扫描对显式非法阈值和结果上限返回 400，缺省值仍由服务端明确提供。

## 3. 已确认缺陷

### P1：移入回收站后错误显示“实际释放空间”（v0.7 已修正用户可见语义）

**证据**

清理成功后，`executeCleanup` 直接执行 `result.Released = record.Size`，并累计为 `released`。
但 `moveToTrash` 只是把文件移入系统回收站；在用户清空回收站前，文件通常仍占用同一磁盘空间。

此外，逻辑文件大小不能代表真实释放量：

- 稀疏文件的逻辑大小可能远大于实际分配空间；
- 多个硬链接指向同一数据时，移动其中一个链接通常不会释放数据块；
- 回收站位于同一卷时，移动本身不会释放卷空间。

**影响**

界面和审计记录会向用户报告并未发生的空间释放，削弱产品最核心的可信度。

**建议**

- v0.6.1 将字段和文案改为“已移入回收站的逻辑大小”或“待回收空间”；
- 不把该值命名为 `releasedBytes`；迁移时保留旧字段含义说明；
- 若未来需要“实际释放”，应在操作前后读取卷可用空间并明确说明其他进程会造成测量噪声；
- 不要为了得到准确数值而自动清空回收站。

**v0.7 处理**

清理接口新增 `movedBytes`，前端确认、提示和审计展示均改为“移入回收站的逻辑大小”；
`released`/`releasedBytes` 继续返回相同数值，仅作为 v0.6 兼容别名。实际卷可用空间仍需用户清空回收站后自行确认。

**验收**

移动普通文件、稀疏文件、单个硬链接和最后一个硬链接时，界面不再声称立即释放对应逻辑大小。

### P1：有效的超长定时扫描会被误标为中断（v0.7 已修复）

**复现**

1. 创建状态为 `walking`、开始时间为 7 小时前的计划扫描会话；
2. 为同一计划保留当前时间的有效租约，表示扫描仍在正常续订；
3. 启动第二个 Space Sheriff 进程并打开同一数据库；
4. 会话被改为 `failed / 上次进程中断`，有效租约仍存在。

本轮已在临时数据库复现上述结果。

**原因**

`recoverInterrupted` 只依据 `scan_sessions.started_at < now - 6h` 判断中断，没有检查
`schedule_leases.acquired_at` 是否仍新鲜。租约续订解决了并发接管，却没有同步修正会话恢复判定。

**影响**

超过 6 小时的慢盘或百万文件扫描，在用户同时打开界面时会短暂显示失败；若进程随后异常退出，
历史状态会永久错误。

**建议**

恢复定时会话时关联同一计划的租约，只在租约缺失或过期时标记失败。前台扫描可使用进程实例表、
心跳字段或独立的短期运行租约，避免继续依赖固定开始时间。

**v0.7 处理**

`recoverInterrupted` 现在排除仍持有新鲜 `schedule_leases` 的计划会话，并新增回归测试覆盖“开始超过 6 小时、
租约仍新鲜”的场景。

**验收**

- 7 小时前开始且租约新鲜的会话保持运行状态；
- 租约过期的同类会话被标记失败；
- 非计划扫描也有可解释的崩溃恢复规则。

### P2：退出接口绕过正常收尾（v0.7 已修复）

**证据**

`POST /api/quit` 在响应后调用 `os.Exit(0)`。这会跳过 `runApplication` 中的 `defer store.Close()`，
也没有取消并等待活动扫描、更新会话状态或完成清理审计。

**影响**

- 活动扫描可能在数据库中保留 `walking` 或 `hashing`；
- 最近 6 小时的残留会话不会在下次启动时立即恢复；
- 若退出与清理操作重叠，审计状态可能需要等待超时后才显示为中断。

**建议**

使用 `http.Server.Shutdown`、根 `context` 和 `WaitGroup` 实现有界优雅退出：先拒绝新任务，取消扫描，
等待会话落库，关闭数据库，最后由 `main` 正常返回。超时后再强制退出，并记录明确状态。

**v0.7 处理**

退出会取消活动扫描，等待扫描完成或 5 秒超时，再调用 `http.Server.Shutdown`；`runApplication` 可以正常返回并执行
数据库关闭 defer。

### P2：前台扫描会静默纠正非法输入（v0.7 已修复）

**证据**

计划扫描严格拒绝非法阈值和结果上限；前台 `/api/scan` 却把负最小值改为 0、非法结果上限改为 2000、
小于 1 MiB 的重复阈值改为 1 MiB。

**影响**

调用方字段错误可能扩大扫描范围或增加哈希工作量，且用户看不到参数已被改变。

**建议**

复用一套扫描参数校验函数并返回 400；只有 UI 明确提供的默认值才应在客户端生成，服务端不静默替换。

**v0.7 处理**

请求字段使用指针区分“缺省值”和“显式传入”，显式负阈值、过小重复阈值和越界结果上限现在返回 400；
缺省字段仍使用明确的安全默认值。

## 4. 重要改进项与待验证风险

### 扫描规模与资源上限

`resultLimit` 只限制大文件结果，不限制目录聚合表、重复候选、按大小分组和哈希分组。
百万文件或很低的重复阈值可能造成显著内存占用和长时间随机 I/O。

建议将候选分组下沉到 SQLite，采用“大小分组 → 快速分块指纹 → 完整 SHA-256”的分阶段流程，
并增加内存、并发读、I/O 速率和最长运行时间指标。优化前先建立 10 万、100 万文件基准，避免凭感觉重构。

### 错误可解释性

扫描目前主要累计 `Errors` 数量，不保留有限的错误样本。用户无法判断错误来自权限、文件消失、
网络卷断开还是哈希失败。建议每次扫描保存按类别聚合的错误数和最多 20 条脱敏/截断样本。

### 哈希期间文件变化

文件元数据在哈希前读取，完整哈希结束后没有再次核对大小、修改时间和文件身份。
建议哈希前后各取一次元数据；变化时丢弃本次哈希并计入 `changed_during_scan`，不写入缓存或重复组。

### 系统任务漂移

系统任务保存可执行文件和数据目录的绝对路径。用户移动便携程序、迁移 `.app` 或还原数据目录后，
任务可能继续指向旧位置。建议启动时对期望配置与系统任务进行只读检查，明确提示“需要修复”，
由用户确认后重新注册。

### 平台与可访问性验证缺口

- Windows 11：真实创建、注销/重启后触发、睡眠唤醒、中文账户路径、停用和删除；
- 签名 macOS `.app`：移动应用、登录启动、睡眠唤醒、SMAppService 迁移；
- 键盘完整操作、VoiceOver/Narrator、200% 缩放、高对比度和焦点可见性；
- 断电、数据库磁盘已满、外置盘拔出和超过 6 小时扫描。

## 5. 测试与工程改进

覆盖率 66.0% 可以作为当前基线，但不能单独作为发布质量结论。以下路径仍接近或等于 0%：
真实回收站、真实平台任务安装/移除、HTTP 监听生命周期、优雅退出、磁盘根目录枚举和浏览器打开。

建议增加以下门槛：

1. 每个已确认缺陷先有失败测试，再实施修复；
2. PR 必须通过 race、vet、Python、前端语法、四平台构建和 Windows 测试交叉编译；
3. 发布分支必须通过 Windows 与 macOS 两台干净虚拟机的系统任务脚本；
4. 数据库迁移必须覆盖 v1、v2、v3 真实 fixture、磁盘已满和高版本拒绝；
5. 性能门槛同时记录耗时、峰值 RSS、数据库增长、读取字节和取消延迟；
6. 不追求整体覆盖率数字的机械上涨，优先覆盖清理、恢复、系统任务和生命周期边界。

## 6. 版本路线图

### v0.6.1：正确性与生命周期修复

目标：修复错误计量、长扫描恢复、优雅退出和参数校验一致性，不增加新功能。

发布门槛：四个缺陷均有回归测试；现有测试全绿；清理审计字段迁移兼容旧库；活动扫描退出后没有悬空会话。

### v0.7：计划任务可靠性与提醒（本地实现完成）

已实现预计下次运行时间、最近失败原因、错过运行次数、本地提醒、macOS/Windows 任务漂移检查和“修复任务”入口；
不升级 SQLite schema，仍不自动清理、不引入云端账户或远程策略。

剩余验收项是独立机器上的 Windows 11 真实任务生命周期、签名 macOS 应用和睡眠唤醒验证。

### v0.8：百万文件与慢盘能力

已实现第一阶段：重复候选按 SQLite 会话尺寸分组、首尾快速指纹、可取消的索引/哈希批处理、交互式与定时资源预算、schema v4 迁移和文件量基准入口。

仍需完成：真实磁盘已满/断电/外置盘拔出恢复，单个尺寸组分页和最终结果背压，100,000/1,000,000 文件跨平台基准，以及哈希前后元数据复核和有限错误样本。

预期指标应在基准完成后确定，避免现在承诺缺乏证据的固定速度。

### v0.9：可解释报告与新手引导（原型完成）

已实现第一阶段：新手分析指南、带扫描摘要和引导建议的 JSON、带可读大小与下一步动作的 CSV，
并在导出按钮旁说明文件会保存到浏览器下载目录。原型仍保持本地运行、后台只读和系统路径保护。

下一阶段继续补齐可信分发与无障碍：macOS Developer ID 签名与公证、SMAppService；Windows 安装器与代码签名；
签名更新清单和回滚策略；完成 WCAG 2.2 AA 相关桌面 Web UI 检查以及 VoiceOver/Narrator 回归。

v0.9.1 的错误类别样本已在 v1.0 稳定候选中落地；实际下载目录提示已在导出按钮旁提供。大报告分页仍是后续体验优化，不作为 v1.0 数据契约的一部分。

自动更新必须是可选、可验证且失败可回退；不得改变“本地分析、后台不清理”的产品边界。

### v1.0：稳定版（本地实现完成，外部发布门槛待验收）

已完成稳定契约原型：冻结 SQLite schema v4、CLI `--help/--version`、v1 API 版本信息、错误分类与有限样本、
JSON 诊断摘要和键盘/减少动态效果基线。实现与自动化验证见
[v1.0 设计](../architecture/v1.0-design.md)、[v1.0 测试报告](../testing/v1.0-test-report.md)。

正式发布仍需在独立机器完成双平台安装/升级/降级/卸载矩阵、真实系统任务、百万文件与断电恢复、VoiceOver/Narrator
和签名分发；这些项目没有在当前环境被模拟为“通过”。

## 7. 推荐执行顺序

1. 先做 v0.6.1 的四个正确性修复，保持改动小且逐项测试；
2. 用干净 Windows 11 和签名 macOS 应用补齐真实系统任务验证；
3. 用 v0.8 基准入口测量 10 万和 100 万文件，再收紧存储、哈希和内存门槛；
4. 最后推进签名分发、更新和 v1.0 兼容承诺。

这一路径优先修正用户可见的真实性和数据状态一致性，同时继续保持后台永不自动清理的安全边界。
